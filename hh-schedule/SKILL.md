# hh-schedule — macOS Launchd Scheduling

> **IDE Environment Note:** Throughout this skill, `CLAUDE.md` refers to the project root instruction file. If running in **Claude Code**, use `CLAUDE.md`. If running in **Cursor / Windsurf / TRAE / other IDEs**, use `AGENTS.md` instead. Detection: if `CLAUDE.md` exists in project root, use it; otherwise fall back to `AGENTS.md`.

Turn any Python script into a scheduled task with proper launchd integration.

## When to Use

- User says "配置成定时任务", "每天跑一次", "定时触发"
- User wants a script to run on a schedule
- User asks "支持定时吗?"

## Pre-flight Checklist

Before creating any plist:
1. **Verify the script works manually** — run it once, check output
2. **Confirm the schedule** — what times? how many per day?
3. **Check for conda/venv** — is the script using a specific Python environment?
4. **⚠️ STOP MECHANISM FIRST** — before installing or testing, MUST:
   - Tell user the exact stop command: `launchctl stop {label}`
   - Verify `launchctl stop {label}` actually works (test it after install)
   - If the task runs for 40+ minutes, warn user explicitly about the time commitment
   - Never test a scheduled task when the user hasn't confirmed they know how to stop it
   - If the project's CLAUDE.md has a rule about scheduled task safety, read it first

## Workflow

### Step 1: Analyze the Script

Identify:
- Python path (`which python` or conda env path)
- Working directory (project root)
- Entry point: `python script.py` or `python -m module`
- Any environment variables needed
- Log file location

### Step 2: Generate run.sh

Create `run.sh` in project root (if not exists):

```bash
#!/bin/bash
# Auto-generated by hh-schedule — do not edit manually
export PATH="/usr/local/bin:/usr/bin:/bin:/opt/homebrew/bin:$PATH"
cd "$(dirname "$0")"
exec /path/to/python script.py >> logs/task.log 2>&1
```

Make executable: `chmod +x run.sh`

**If conda env is needed:**
```bash
#!/bin/bash
export PATH="/usr/local/bin:/usr/bin:/bin:/opt/homebrew/bin:$PATH"
source /path/to/miniconda/etc/profile.d/conda.sh
conda activate env_name
cd "$(dirname "$0")"
exec python script.py >> logs/task.log 2>&1
```

### Step 3: Generate launchd plist

Create `~/Library/LaunchAgents/com.{name}.plist`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>Label</key>
    <string>com.{name}</string>
    <key>ProgramArguments</key>
    <array>
        <string>/bin/bash</string>
        <string>/absolute/path/to/run.sh</string>
    </array>
    <key>StartCalendarInterval</key>
    <array>
        <dict>
            <key>Hour</key><integer>12</integer>
            <key>Minute</key><integer>30</integer>
        </dict>
        <!-- Add more intervals as needed -->
    </array>
    <key>StandardOutPath</key>
    <string>/absolute/path/to/logs/task.log</string>
    <key>StandardErrorPath</key>
    <string>/absolute/path/to/logs/task.log</string>
    <key>EnvironmentVariables</key>
    <dict>
        <key>PATH</key>
        <string>/usr/local/bin:/usr/bin:/bin:/opt/homebrew/bin</string>
    </dict>
</dict>
</plist>
```

### Step 4: Generate CLI (if not exists)

Add `install/uninstall/status` commands to the script's module or create a standalone scheduler module:

```python
# Key commands:
# install:   cp plist to ~/Library/LaunchAgents/ && launchctl load
# uninstall: launchctl unload && rm plist (warns if running)
# status:    launchctl list | grep {name}
```

Use the pattern from existing project schedulers (`src/scheduler.py` or `phase3_faq/scheduler.py`).

### Step 5: Install & Verify

```bash
python -m {module}.scheduler install
launchctl list | grep {name}    # should show the job
launchctl start {name}           # manual trigger test
tail -f logs/task.log           # verify it runs
```

### Step 6: Document

Generate `docs/quick-start/scheduler.md`:
```markdown
# Scheduler: {task name}

## Schedule
- Times: {list}
- Config: `config/{name}.toml` → `[schedule].times`

## Commands
python -m {module}.scheduler install     # Install
python -m {module}.scheduler uninstall   # Uninstall (stops running process)
python -m {module}.scheduler status      # Check status
launchctl start {label}                   # Manual trigger

## Stop
launchctl stop {label}                    # Stop running process
python -m {module}.scheduler uninstall    # Remove entirely

## Debug
tail -f logs/task.log                     # Watch logs
launchctl list | grep {label}             # Check if installed
```

## Important: Always Tell the User

Before concluding, explicitly tell the user:
1. **How to trigger manually**: `launchctl start {label}`
2. **How to stop**: `launchctl stop {label}`
3. **How to view logs**: `tail -f logs/task.log`
4. **How to uninstall**: `python -m {module}.scheduler uninstall`

**Never test a scheduled task without the user knowing how to stop it.**

## Red Flags

- Installing/testing a scheduled task without first verifying `launchctl stop` works
- Not warning user about task duration (40+ minute tasks block normal work)
- Assuming the user remembers how to stop — tell them explicitly every time
- Generating a plist without also generating the stop/debug documentation (Mode A template)
